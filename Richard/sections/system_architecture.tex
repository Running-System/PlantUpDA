\section{Plant Up! System Architecture and Implementation}

The previous section outlined the protocol-level and distributed-systems concepts required for the evaluation of MQTT and REST. Building on that foundation, this section presents the concrete architecture of ``Plant Up!'' as it was implemented for the practical comparison. The focus lies on the interaction between the edge node, the backend services, and the application layer, with particular attention to how sensor data is structured, transmitted, and processed throughout the system \cite{nistNoT2016, cheThreeTier}.

\subsection{System Overview and Vision}
The ``Plant Up!'' platform integrates distributed IoT hardware, a scalable cloud microservices backend, and a mobile application into one ecosystem \cite{nistNoT2016, fowlerMicroservices}. This setup represents a practical realization of the Social Internet of Things (SIoT) concept outlined previously in the theoretical background \cite{atzoriSiot2012, jungWeon2025}. It enables plants to communicate their environmental status digitally to their caretakers. The primary objective of this architecture is the collection of environmental data from custom edge devices, the synchronization of this data through the cloud, and its presentation to users through lightly gamified interactions \cite{deterding2011, barariGamification2024}.

To realize this vision, the architecture had to address three critical requirements:
\begin{itemize}
    \item Low-latency sensor synchronization: When a plant requires attention, the user is expected to be notified promptly. The feedback loop between biological need and human action should therefore be closed as quickly as possible.
    \item Energy-efficient operation: IoT devices intended for casual home use must be designed for long-term deployment. This requires conserving battery power through deep sleep cycles and minimizing radio usage \cite{espIdfS3SleepModes, esp32s3Datasheet2026}.
    \item Distributed consistency: Because data is distributed across User, Social, and Hardware domains, the system must maintain a coherent state even during periods of localized network instability \cite{richardsonDbPerService, designGurusCAP}.
\end{itemize}

These requirements informed the main architectural decisions, ranging from the hardware design to the structure of the microservices. As a result, the system follows a clearly separated multi-layered approach consisting of the Edge Node, the Cloud Layer, and the Application Layer \cite{nistNoT2016, cheThreeTier}.

\subsection{Hardware Layer: The Edge Node}
Within the scope of this chapter, the hardware layer is relevant primarily because it defines the constraints under which MQTT and REST were evaluated. It forms the physical sensing infrastructure of the project and acts as the bridge between the plant environment and the cloud backend. At the center of this design is the ESP32-S3 microcontroller together with sensors for temperature, humidity, light, soil moisture, and electrical conductivity \cite{esp32s3Datasheet2026, boniecki2023smartSensors}. Because the system is battery-powered, the device spends most of its operational time in deep sleep \cite{espIdfS3SleepModes}. Its active cycle therefore follows a defined sequence:

\begin{enumerate}
    \item Acquisition: The microcontroller wakes up, temporarily powers the attached sensors, and captures a brief environmental snapshot.
    \item Serialization: The recorded sensor readings are packed into a compact JSON format.
    \item Transmission: The data packet is transmitted to the cloud via MQTT or REST, after which the device returns to deep sleep.
\end{enumerate}

\subsubsection{Component Selection and Sensor Interface}
Hardware selection involves a trade-off between technical capability and energy longevity. For this chapter, the relevant point is not the full hardware design in isolation, but how the selected components influence payload creation, wake-up behavior, and communication with the backend. With these constraints in mind, the following components were chosen for the ``Plant Up!'' edge node.

Microcontroller: Espressif ESP32-S3
The ESP32-S3 acts as the central processing unit. It was selected for its balance between computational power and energy efficiency. It features a dual-core processor together with built-in Wi-Fi and Bluetooth connectivity \cite{esp32s3Datasheet2026}. Of particular relevance here is its Ultra-Low Power (ULP) co-processor, which allows the main CPU to remain asleep while basic environmental monitoring continues in the background \cite{espIdfS3Ulp}.

Soil Moisture Sensor: HiLetgo LM393
The HiLetgo LM393 measures soil moisture and provides the readings required to trigger watering-related notifications. In the context of this chapter, its relevance lies primarily in the fact that it contributes to the telemetry payload transmitted by the edge node. Low-cost soil moisture sensors require careful interpretation because their readings can be affected by calibration and environmental factors \cite{chowdhuryCalibration2022}.

Light Sensor: HiLetgo BH1750
The BH1750 is a digital I2C sensor that provides lux readings \cite{bh1750Datasheet, nxpI2cSpec}. This data allows the system to assess whether a plant is receiving adequate light exposure based on its species and to generate corresponding notifications.

Electrical Conductivity (EC) Sensor: DFRobot Gravity V2
The DFRobot Gravity Analog EC Sensor is used to measure the electrical conductivity of the soil, a metric correlated with nutrient concentration.
\begin{itemize}
    \item \textit{Relevance of EC:} Electrical conductivity correlates with nutrient levels. A plant may therefore be adequately watered while still showing nutrient-related problems. Integrating this sensor extends the system beyond a simple watering alarm and supports a broader view of plant health \cite{boniecki2023smartSensors}.
\end{itemize}

Power Supply and Sustainability
To support remote long-term operation, the device pairs a lithium-ion battery with a small 0.5\,W photovoltaic solar panel. This combined setup is intended to remain self-sustaining under suitable light conditions, while a USB-C port is included as a fallback charging option. Energy harvesting combined with local storage is a common strategy for extending the deployment lifetime of low-power IoT nodes \cite{aliEnergyHarvesting2025}.

A particularly important design decision at this stage is the timestamping of every measurement at the source, directly on the edge node itself. This approach preserves the event time of the observation and ensures that even during extended periods of network unavailability, the backend can reconstruct the historical data timeline based on the original recording time rather than on a delayed arrival time at the server \cite{akidauDataflow2015}.

\subsection{Microservice Architecture Design}
The backend infrastructure is structured as a collection of microservices organized around isolated Supabase schemas. In this architecture, each schema functions as a bounded context \cite{fowlerMicroservices, evansDDD2003, azureMicroserviceBoundaries}, encapsulating a designated domain:
\begin{itemize}
    \item \texttt{user\_schema}: This area manages user profiles, activity streaks, and virtual wallets.
    \item \texttt{social\_media\_schema}: Responsible for community content, including user posts, comments, and public plant profiles.
    \item \texttt{microcontroller\_schema}: Acts as the centralized data store for incoming raw sensor readings.
    \item \texttt{gamification}: Houses the core game logic, including quests, progress tracking, and accumulated XP.
\end{itemize}

This strict separation provides practical development and operational benefits. For instance, modifications to the quest system can be carried out without risking disruptions to the sensor ingestion pipeline. Consequently, failures isolated in one domain are unlikely to cascade into the others. The pattern also reflects the microservice principle that each service should own its persistent data, even when implemented through separate schemas in a shared relational platform \cite{richardsonDbPerService, supabaseCustomSchemas}.

By way of example, the \texttt{Plants} table located in the social schema links a user's plant to its ideal growing conditions, which are stored independently in \texttt{Plant\_data}. This setup allows other services to retrieve the required botanical reference data without creating unnecessary dependencies within the social database \cite{azureMicroserviceBoundaries}.

\subsection{Real-Time Data Synchronization Mechanism}
One of the central challenges in the ``Plant Up!'' architecture is balancing real-time data delivery against the need for energy conservation on remote sensor devices. While users expect to see fresh data reflected in the application promptly, the sensor nodes cannot afford the energy cost of maintaining fully persistent network connections \cite{espIdfS3SleepModes, jara2023mqtt}. It is therefore necessary to explain the reasoning behind the adopted synchronization strategy.

During the planning phase, two primary approaches were evaluated for handling sensor-to-cloud communication:
\begin{itemize}
    \item REST (HTTPS): The standard approach of the modern web. It is highly structured and universally supported, which makes it well-suited for traditional user-facing API interactions \cite{fieldingRest2000, rfc7230Http}. When it is used to transmit small, frequent sensor packets, however, the required connection overhead becomes substantial \cite{jara2023mqtt}.
    \item MQTT: A protocol designed specifically for constrained IoT scenarios. It is lightweight and operates on a publish/subscribe model, a structure that aligns well with the constraints of battery-powered microcontrollers such as the ESP32 \cite{oasisMqtt5, hivemqPubSub}.
\end{itemize}

Ultimately, a hybrid approach was adopted in order to leverage the strengths of both protocols. MQTT is used exclusively for the uplink sensor-to-cloud communication path because its lightweight binary format and broker-based communication model help minimize the energy expenditure required for each transmission cycle \cite{oasisMqtt5, jara2023mqtt}. By contrast, the user-facing mobile application continues to communicate with the backend via standard REST APIs because smartphones do not face the same energy constraints and benefit from the request-response semantics of HTTP when loading complex user profiles or social feeds \cite{fieldingRest2000, rfc7230Http}.

Following this architecture, the deployed IoT devices publish their sensor data via MQTT to a central broker. A dedicated backend service subscribes to the relevant topics and persists the incoming data stream into the database. The mobile application then retrieves this processed data through standard RESTful endpoints \cite{hivemqPubSub, supabase_postgresdb_2026}.

\subsection{User Engagement and Data Processing}
The social and gamification components integrated into ``Plant Up!'' are not merely cosmetic additions; they serve as the primary mechanism for driving user engagement over time \cite{deterding2011, hamariGamification2014, barariGamification2024}. This logic is housed within the \texttt{gamification} schema, where it monitors the data streams arriving from the other system layers.

The system relies on three core database tables:
\begin{itemize}
    \item Quests: The catalog of available challenges, including tasks such as ``Water your Monstera'' or ``Check the light level''.
    \item User\_quests: Maintains a record of the user's progress on assigned quests.
    \item player\_stats: Stores cumulative behavioral statistics, including total XP and current level.
\end{itemize}

The integration between the raw sensor layer and the higher-level gamification layer functions as follows. When the sensor layer detects a sharp increase in soil moisture, the system infers that the user has recently watered the plant. The processing service then triggers an update to the user's quest progress. This creates a direct link between physical action and digital feedback, a mechanism that supports motivation by making progress visible and responsive \cite{ryanDeci2000SDT, spinifyGamification}.

This modular design helps maintain a clear operational separation between the engagement logic and the underlying hardware infrastructure. Game mechanics such as adjusting quest difficulty or running temporary seasonal events can therefore be modified independently without requiring a firmware update on the deployed edge devices \cite{fowlerMicroservices, richardsonDbPerService}.
