\section{Theoretical Background}

Having established the core challenges of latency, energy efficiency, and data consistency in the previous sections, it is helpful to outline the theoretical foundations needed to understand the architectural decisions made in this thesis. This chapter covers the shift toward microservices architecture, the physical constraints of IoT hardware, the characteristics of communication protocols, and the fundamentals of distributed data consistency.

\subsection{Microservices Architecture (MSA)}
Microservices Architecture (MSA) represents a fundamental shift in modern software design. It organizes applications not as single monolithic systems, but as suites of small, relatively autonomous services that collaborate through well-defined interfaces \cite{awsMicroservices}. In a traditional monolithic setup, almost all functionality, ranging from user management to data processing, is tightly coupled within one large codebase. While this approach can simplify initial development and deployment, it often becomes an obstacle to scalability and fault tolerance as the application expands in complexity \cite{fowlerMicroservices}.

MSA addresses this limitation by treating the application as a collection of independent services. Each service generally runs in its own isolated process and communicates through lightweight channels, often using HTTP APIs or messaging systems \cite{newmanBuilding}. Each service takes responsibility for a specific business domain. For the ``Plant Up!'' platform, this architectural style is well-suited because it allows different parts of the system to be developed, modified, and scaled independently. For example, the service responsible for ingesting large volumes of sensor readings can be scaled horizontally during peak periods without placing the same load on the social feed service.

To manage this, the ``Plant Up!'' backend is organized around domain-specific schemas within Supabase, which function as the data stores for these separate microservices:
\begin{itemize}
    \item \texttt{user\_schema}: This primarily manages user identity, authentication, and personal statistics such as activity streaks.
    \item \texttt{social\_media\_schema}: Responsible for community features, including user posts and public plant profiles.
    \item \texttt{gamification}: Houses the logic for quest progression, experience points (XP), and virtual rewards.
    \item \texttt{microcontroller\_schema}: Acts as a dedicated data store for the raw sensor telemetry arriving from the IoT edge nodes.
\end{itemize}

A clear example of this separation can be found in the storage of the sensor readings themselves. They reside in an isolated table that is structurally decoupled from the standard user data:

From a practical perspective, maintaining this structural boundary improves overall system robustness. If the sensor-reading service encounters an unexpected failure, the resulting downtime is less likely to propagate into the gamification or social interaction features.

\subsection{Core Characteristics of Microservices in IoT}
Applying Microservices Architecture to the Internet of Things introduces a distinct set of challenges. IoT systems are inherently asynchronous and event-driven. Moreover, they must operate under the unpredictable conditions of physical home environments.

\subsubsection{Autonomy and Database per Service}
One of the established principles of MSA is the concept of a ``Database per Service''. This principle states that microservices should be decoupled not only at the code boundary, but also at the data layer \cite{richardsonDbPerService}. It helps prevent the scenario in which modifying a database table for one service inadvertently breaks the functionality of another service that depends on the same schema. In the context of ``Plant Up!'', the Gamification Service therefore maintains its own record of player statistics, separate from the raw stream of incoming environmental sensor data.

\subsubsection{Scalability and Elasticity}
IoT workloads are characteristically intermittent. Long periods of sensor silence may be followed by sudden bursts of transmission activity whenever many devices wake up to report their status changes. MSA helps accommodate this variance by allowing the Ingestion Service to scale horizontally without allocating the same level of resources to the more stable Social Service.

\subsection{Internet of Things (IoT) Constraints and Hardware}
At the hardware foundation of ``Plant Up!'' is the ESP32-S3 microcontroller, a System-on-Chip (SoC) produced by Espressif Systems \cite{esp32s3Datasheet}. Despite offering useful processing power, it remains constrained by battery life. The choice of communication protocol directly determines how long the device must remain in an energy-intensive active state and therefore has a direct effect on battery longevity in household use.

\subsubsection{Power Consumption and Sleep Modes}
The ESP32-S3 architecture provides several distinct power modes, each with a different energy consumption profile. Understanding these modes is essential for the architectural design:
\begin{itemize}
    \item Active Mode: Almost all integrated components, including the CPU, Wi-Fi radio antenna, and various peripherals, are fully powered up. In this state, the device typically consumes between 160 and 260 milliamperes (mA) \cite{lastMinuteActive}. Minimizing time spent in this mode is critical for energy conservation.
    \item Modem Sleep: The main CPU remains active, allowing script processing to continue, but the radio is temporarily disabled. Power consumption drops to roughly 20--30\,mA \cite{lastMinuteActive}.
    \item Deep Sleep: The main CPU, the Wi-Fi module, and the primary RAM are powered down. Only the Ultra-Low Power (ULP) coprocessor and the Real-Time Clock remain active. Current consumption drops to about 10\,\textmu A--150\,\textmu A \cite{esp32s3Datasheet}.
\end{itemize}

\subsubsection{The Wake-Up Tax}
While deep sleep provides substantial energy savings, it also introduces a noticeable ``wake-up tax''. Upon waking to perform a reading, the device must re-initialize the Wi-Fi module, reconnect to the access point, and negotiate a fresh IP address on the local network. This process typically takes between 1 and 3 seconds and consumes around 150\,mA on average before a single byte of useful data is transmitted \cite{adafruitWake}. The choice of communication protocol therefore has a direct impact on the amount of additional handshake overhead introduced during this transition.

\subsection{Communication Protocols: MQTT vs. REST}
Choosing the primary communication protocol is one of the most important architectural decisions at the data layer. It has a direct effect on energy efficiency, latency, and long-term reliability. This subsection examines the two protocols considered for the ``Plant Up!'' sensor layer.

\subsubsection{MQTT (Message Queuing Telemetry Transport)}
MQTT operates as a lightweight binary messaging protocol that was designed for networks characterized by unreliability and limited bandwidth \cite{psiborg2024mqtt}. Rather than relying on direct point-to-point connections, it uses a publish-subscribe routing model.

Architecture and Decoupling:
Unlike the standard REST approach, which connects two endpoints directly, MQTT introduces a central broker to act as an intermediary. The sensor, acting as the publisher, sends data to a designated topic such as \texttt{plantup/sensor/01} without requiring knowledge of which backend services consume that data. The broker handles message routing and forwards the data to all subscribed backend services, such as the Ingestion Service. This architecture decouples devices both in space, because they do not need to know each other's IP addresses, and in time, because messages can be queued temporarily if a consuming service is offline or unreachable.

Packet Structure:
MQTT further improves efficiency through its binary transmission format, which reduces textual overhead. The fixed transmission header requires only 2 bytes of space~\cite{oasisMqtt31}. This contrasts with traditional HTTP headers, which can accumulate to several hundred bytes per message~\cite{rfc7230Http}.

Quality of Service (QoS):
MQTT further differentiates itself by providing three levels of delivery assurance~\cite{oasisMqtt31}:
\begin{itemize}
    \item QoS 0 (At most once): A fire-and-forget approach. It consumes the least energy, but messages that are lost in transit are not retransmitted.
    \item QoS 1 (At least once): Prioritizes guaranteed delivery by requiring a return acknowledgment (PUBACK). This level is generally suitable for transmitting critical sensor data.
    \item QoS 2 (Exactly once): Uses a four-step handshake intended to guarantee exactly-once delivery. However, this level usually introduces too much overhead for severely constrained battery-powered devices.
\end{itemize}

\subsubsection{REST (Representational State Transfer)}
REST remains the dominant architectural style of the modern web and relies on standardized HTTP methods~\cite{rfc7230Http}. It follows a synchronous and resource-oriented model.

Request-Response Model:
REST adheres to a traditional client-server paradigm. The client issues a formatted request, such as GET or POST, and then waits for the server to respond before proceeding.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{images/rest_converted.png}
    \caption{REST Request-Response Workflow: Stateless clients must establish a new connection for every request, incurring significant overhead \cite{dreamfactory2024rest}.}
    \label{fig:rest_diagram}

Statelessness and Overhead:
Under REST principles, the server retains no state between sequential requests. Consequently, each transmission must carry its own context, including authentication tokens, headers, and metadata. Furthermore, if the IoT device enters deep sleep between readings, it must perform a full TCP three-way handshake and often an additional TLS handshake for \textit{every single transmission}. This mandatory connection overhead makes REST less energy-efficient than a partially persistent MQTT session for frequent, small data packets.

\subsection{Data Consistency and the CAP Theorem}
In distributed systems, the CAP theorem states that consistency, availability, and partition tolerance cannot all be fully guaranteed at the same time in the presence of a network partition \cite{brewerCap, designGurusCAP, jaiswalCAP}.

For a project like ``Plant Up!'', partition tolerance (P) is not optional because home sensor networks are inherently unstable and intermittent. This practical constraint forces an architectural choice between prioritizing CP or AP behavior:
\begin{itemize}
    \item CP (Consistency + Partition Tolerance): Under this model, incoming requests are rejected if strong consistency cannot be guaranteed across the network, which increases the risk of unavailable functionality during a prolonged disruption.
    \item AP (Availability + Partition Tolerance): Under this model, data is accepted and requests continue to be served even if some nodes are temporarily out of sync with the master log.
\end{itemize}

``Plant Up!'' ultimately follows an AP-oriented design and relies on eventual consistency. In practical terms, it is acceptable for a user to occasionally observe a soil moisture value that is a few seconds out of date, provided that the mobile application remains responsive and stable. Under this model, the deployed MQTT broker serves as a buffering system that holds incoming sensor messages during short network disruptions and ensures that they eventually reach the downstream microservices layer.
