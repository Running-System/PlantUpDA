\section{Experimental Evaluation of MQTT vs.\ REST}

\subsection{Introduction to the Experiment}
The theoretical analysis presented in Section~2 established that MQTT offers significant advantages over REST in terms of protocol overhead and energy efficiency. However, theoretical analysis alone is insufficient to guide architectural decisions for production systems. Quantitative, empirical data is required to determine the actual magnitude of the performance difference under realistic operating conditions. This experiment was designed to provide precisely such evidence, directly addressing the research question posed in the introduction by measuring the performance gap between MQTT and REST on the actual ``Plant Up!'' hardware and backend infrastructure.

\subsection{Experimental Setup}
To ensure the reliability and reproducibility of the results, the experimental environment was rigorously standardized. The setup consisted of three main components:

\begin{enumerate}
    \item The Device (Edge Node): A standard ESP32-S3 unit, identical to the production hardware deployed in plant pots, was used. The firmware was modified to isolate the protocol-specific transmission time from the remainder of the boot process, using high-precision microsecond timers.
    \item The Network: Rather than using an idealized laboratory network, the device was connected to a standard residential 2.4\,GHz Wi-Fi router with average signal strength (RSSI between $-65$\,dBm and $-75$\,dBm). This decision was made to capture protocol behavior under the realistic network conditions that end users would experience.
    \item The Backend: All data was transmitted to the live Supabase production database. This ensures that the latency measurements include the complete end-to-end path: network travel time, database insertion, and trigger execution.
\end{enumerate}

To eliminate the variable of sensor reading time, a static, pre-defined JSON payload was transmitted in every trial. This guarantees that the payload size remained constant across all 200 test runs.

\subsection{Methodology and Metric Acquisition}
Data collection was fully automated to eliminate human error. The firmware executed a rigid measurement loop for each trial:
\begin{enumerate}
    \item Wake Up: The device boots from deep sleep.
    \item Connect: The device negotiates with the Wi-Fi router.
    \item Send: The JSON payload is serialized and transmitted using either HTTP POST or MQTT PUBLISH.
    \item Verify: The device waits for server confirmation (HTTP 200 or MQTT PUBACK).
    \item Sleep: The elapsed time is logged, and the device immediately returns to deep sleep.
\end{enumerate}

Three metrics were captured:
\begin{itemize}
    \item End-to-End Latency: The total elapsed time from boot to server confirmation. This metric encompasses all phases: handshakes, serialization, and network propagation.
    \item Effective Payload Size: Captured using Wireshark packet analysis, this metric reveals the true protocol overhead. While the application payload may be 50 bytes, the total bytes transmitted including protocol headers can be significantly larger.
    \item Reliability: The ratio of successfully persisted packets to total transmission attempts, measured over 100 trials per protocol.
\end{itemize}

The results reveal a substantial performance gap between the two protocols. Figure~\ref{fig:results_table_img} presents the aggregated results from the 100 test runs per protocol.

MQTT demonstrated significantly superior performance across all measured metrics. The average end-to-end latency for MQTT was 185\,ms, compared to 612\,ms for REST---a reduction of approximately 70\%. The difference in data usage was equally pronounced: MQTT consumed approximately 312 bytes per transmission cycle, while REST required approximately 982 bytes.

\subsection{Discussion}
These results confirm the theoretical predictions regarding the overhead of HTTP in battery-constrained IoT scenarios. The substantial difference in latency is primarily attributable to the connection establishment process. With REST, every transmission requires a full TCP three-way handshake and a TLS secure socket negotiation. The device expends more time and energy on connection setup than on the actual data transfer.

MQTT, while also requiring an initial connection, eliminates the verbose text-based headers characteristic of HTTP (such as \texttt{User-Agent} and \texttt{Content-Type}). Its binary protocol structure and more efficient handshake mechanism result in significantly lower per-transmission overhead.

An additional observation was that REST exhibited lower reliability under adverse network conditions. During periods of network instability, time-constrained HTTP requests occasionally timed out and failed entirely, whereas MQTT's asynchronous nature and built-in retry mechanisms allowed it to deliver packets through smaller windows of connectivity.

\subsection{Conclusion}
This experiment provides empirical evidence that MQTT is the superior protocol choice for the ``Plant Up!'' sensor layer. It achieves approximately three times lower latency and significantly reduced data usage compared to REST. While REST remains appropriate for the mobile application layer---where its request-response semantics are well-suited for loading user profiles and social content---the ESP32-S3 hardware cannot sustain the overhead of HTTP for regular sensor reporting. Based on these results, MQTT was adopted as the standard protocol for all telemetry ingestion, as it is the only viable option for achieving sufficient battery longevity in a consumer-facing product.
