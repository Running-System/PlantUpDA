\section{Experimental Evaluation of MQTT vs.\ REST}

While the theoretical analysis presented in Section~2 suggested that MQTT offers advantages over REST with regard to protocol overhead and energy efficiency, theoretical considerations alone are not sufficient to justify architectural decisions in practice. Quantitative evidence is required to determine how large these differences are under realistic operating conditions. For this reason, the system was evaluated through a targeted experiment using the actual ``Plant Up!'' hardware and backend infrastructure.

\subsection{Experimental Setup}
To derive meaningful conclusions, the experimental environment was standardized as far as possible in order to improve reproducibility. The setup consisted of three primary components:

\begin{enumerate}
    \item The Device (Edge Node): The tests used a standard ESP32-S3 unit identical to the hardware intended for deployment in the plant pots. For measurement purposes, the firmware was modified so that the protocol-specific transmission time could be isolated from the rest of the boot process by using high-precision microsecond timers.
    \item The Network: Instead of relying on an ideal laboratory connection, the device was connected to a standard residential 2.4\,GHz Wi-Fi router with an average signal strength between $-65$\,dBm and $-75$\,dBm. This decision was made in order to observe protocol behavior under the network conditions typically encountered by end users.
    \item The Backend: All test data was routed to the live Supabase production database. This ensured that the latency measurements represented the complete end-to-end path, including network transfer, database insertion, and trigger execution.
\end{enumerate}

In order to avoid confounding variables such as differences in sensor-reading time, a static pre-defined JSON payload was transmitted in every trial. This ensured that the payload size remained consistent across the 200 individual test runs.

\subsection{Methodology and Metric Acquisition}
To reduce the influence of human handling, the data collection process was largely automated. For each trial, the firmware executed the following measurement loop:

\begin{enumerate}
    \item Wake Up: The microcontroller begins its boot sequence from deep sleep.
    \item Connect: A connection is negotiated with the local Wi-Fi router.
    \item Send: The predefined JSON payload is serialized and transmitted, varying only in the underlying method used for transmission (HTTP POST or MQTT PUBLISH).
    \item Verify: The device waits for confirmation from the server, expecting either an HTTP 200 status or an MQTT PUBACK.
    \item Sleep: The elapsed time is recorded locally, and the device immediately returns to deep sleep.
\end{enumerate}

During this cycle, three primary metrics were monitored:
\begin{itemize}
    \item End-to-End Latency: The total time elapsed from the beginning of the boot sequence to the receipt of server confirmation. This metric includes handshakes, serialization delays, and network propagation.
    \item Effective Payload Size: To assess true protocol overhead, Wireshark packet analysis was used. Although the application payload itself was only about 50 bytes, the total volume of transmitted data increased once protocol formatting and headers were included.
    \item Reliability: The ratio of successfully persisted packets to total transmission attempts, measured over 100 trials for each protocol.
\end{itemize}

Packet reception and persistence were verified by executing a targeted SQL query directly on the backend infrastructure.

The results indicate that MQTT outperformed REST across the measured categories. The average end-to-end latency for MQTT was 185\,ms, whereas REST required 612\,ms on average, which corresponds to a reduction of roughly 70\%. A similar pattern was visible in data usage: MQTT transmissions involved approximately 312 bytes per cycle, compared with around 982 bytes for REST.

\subsection{Discussion}
Viewed in context, these results confirm the theoretical expectations regarding HTTP overhead in battery-constrained IoT applications. The recorded latency gap appears to be driven primarily by connection establishment. For REST, each transmission requires a full TCP three-way handshake followed by a TLS negotiation~\cite{rfc8446Tls, emqxMqttVsHttp}. Under these conditions, the device spends a substantial portion of its active time establishing the connection rather than transmitting the sensor data itself.

By contrast, MQTT, although it still requires initial negotiation, avoids much of the verbose text-based header information typical of HTTP, such as \texttt{User-Agent} and \texttt{Content-Type}~\cite{iotForAllMqttHttp}. Its binary structure and more streamlined communication pattern contribute to a lower per-transmission overhead.

Beyond per-device efficiency, these differences have important implications for scalability as the system grows. In a microservices-based IoT architecture, managing large numbers of concurrent inbound connections can become a limiting factor before raw data volume itself becomes problematic. At an early deployment stage of roughly 100 active devices, both protocols perform adequately from a backend perspective. The Supabase infrastructure can absorb occasional bursts of REST-based HTTP requests without noticeable API degradation.

As a hypothetical deployment scales toward 1,000 devices, however, the architectural friction inherent in HTTP becomes more difficult to ignore. Because REST is stateless and synchronous, each sensor node must establish a fresh TLS connection for every measurement cycle. This introduces recurring overhead on the API Gateway, requiring the backend to repeatedly allocate memory and processing time for connection setup and teardown~\cite{emqxMqttVsHttp}. MQTT reduces much of this overhead through the use of persistent TCP connections. The broker maintains an active session with registered devices and receives a continuous stream of lightweight binary packets rather than a large number of independent requests~\cite{iotForAllMqttHttp, comeStarMqttHttp}.

At a peak of around 10,000 devices, these differences become even more relevant. Attempting to ingest data from 10,000 sensors simultaneously via REST would risk triggering rate limits, exhausting API connection pools, and overwhelming database insertion queues~\cite{awsApiLimits, nginxWorkerLimits}. Under an MQTT-based architecture, the broker can absorb transmission spikes by queueing messages while maintaining a large number of simultaneous device connections~\cite{dreamFactoryEdgeMqtt, emqxBenchmark}. The backend microservices can then process this queue at a sustainable pace and persist the data into the \texttt{microcontroller\_schema} without overloading the core database engine~\cite{hivemqPubSub, oasisMqtt5}.

This asynchronous design also improves horizontal scaling potential. If the ingestion service falls behind during a large burst of queued data, additional worker instances can be provisioned to drain the queue more quickly. Under REST, the same traffic spike would impact the database more directly and could lead to transmission failures before auto-scaling reacts.

An additional observation from the trials concerns reliability during unstable network conditions. When the Wi-Fi environment became temporarily unstable, the time-constrained HTTP requests occasionally timed out and failed. MQTT's asynchronous architecture, together with its built-in Quality of Service (QoS) retry mechanisms, proved better suited to operating under partial connectivity.

\subsection{Energy Implications of Protocol Selection on ESP32-Based IoT Devices}
While latency and system scalability are central aspects of this comparison, battery longevity remains the most important practical constraint in a residential IoT environment. For the ``Plant Up!'' ecosystem, the rate of energy depletion directly affects the long-term viability of the product. It is therefore necessary to examine how the measured protocol overhead translates into physical power consumption.

To establish a baseline for this analysis, the power consumption profile of the ESP32-S3 microcontroller must be considered. The device operates across several distinct power states, each with a different current draw. For this estimate, approximate values derived from the manufacturer's documentation are used. During \textit{Active} mode, when the processor is operational but the radio is idle, the device consumes around 35\,mA. When the Wi-Fi modem is enabled and actively negotiating or transmitting data, current draw rises significantly, reaching approximately 240\,mA on average~\cite{lastMinuteActive, esp32s3Datasheet2026}. In \textit{Deep Sleep}, where almost all peripherals are powered down, the current consumption drops to roughly 10\,\textmu A~\cite{esp32s3Datasheet2026}.

To quantify the energy consumed during a single telemetry transmission cycle, the standard electrical energy formula can be applied:

\begin{equation}
E = I \times V \times t
\end{equation}

In this equation, $E$ represents energy in Joules, $I$ the electrical current in Amperes, $V$ the operating voltage, and $t$ the duration of the active transmission state in seconds. Because the operating voltage and transmission current remain broadly constant during active Wi-Fi usage, the dominant factor in this calculation is time.

This relationship places the recorded latency measurements into practical context. During the experiment, the average end-to-end latency for MQTT was 185\,ms (0.185\,s). Assuming an average active current of 240\,mA during this phase, the energy consumed per MQTT transmission cycle can be estimated as follows:

\begin{equation}
E_{\text{MQTT}} \approx 0.240\,\text{A} \times 3.3\,\text{V} \times 0.185\,\text{s} \approx 0.146\,\text{Joules}
\end{equation}

For REST, the average transmission latency was 612\,ms (0.612\,s). Applying the same hardware parameters yields:

\begin{equation}
E_{\text{REST}} \approx 0.240\,\text{A} \times 3.3\,\text{V} \times 0.612\,\text{s} \approx 0.484\,\text{Joules}
\end{equation}

These results indicate a substantial difference at the device level. A single REST transmission consumes nearly 3.3 times as much energy as a comparable MQTT transmission~\cite{jara2023mqtt}. This suggests that the overhead associated with HTTP is not merely a theoretical inefficiency; it has a measurable effect on the battery consumption of the device. Under real deployment conditions, where retries may be necessary, this energy gap could become even larger.

The effect becomes more significant when extrapolated over a realistic operating period. If the ``Plant Up!'' sensor node reports telemetry once per hour, it performs roughly 8,760 updates per year. Under an MQTT architecture, the transmission overhead alone would account for approximately 1,280 Joules per year. Under a REST-based architecture, the same workload would consume more than 4,240 Joules annually.

This increased energy demand also has secondary practical effects. If a REST-based device depletes its battery more quickly than an MQTT-based alternative, the frequency of battery replacement or solar recharge increases. In a consumer setting, frequent manual intervention undermines the intended convenience of an autonomous sensor system and may reduce long-term user acceptance.

From an architectural perspective, this analysis shows that protocol efficiency has different levels of importance depending on where it is applied within the system. In the cloud backend, the difference between parsing 312 bytes and 982 bytes is relatively minor. At the network edge, however, within the strict limits of a battery-powered ESP32, these additional milliseconds directly affect device lifetime. For this reason, optimizing protocol overhead at the device layer is one of the most effective ways to improve long-term hardware longevity.

\section{Conclusion}
The experimental data indicates that MQTT is the more suitable protocol for the sensor layer of the ``Plant Up!'' ecosystem. Its lower latency and reduced data overhead make it preferable to REST for battery-constrained telemetry ingestion. REST nevertheless remains appropriate in the mobile application layer, where its request-response model is well suited to fetching user profiles and social content. For the ESP32-S3 hardware used at the edge, however, the repeated overhead of HTTP is too costly for frequent sensor reporting. MQTT was therefore selected as the primary protocol for telemetry ingestion because it offers the better balance between responsiveness, scalability, and battery longevity.
