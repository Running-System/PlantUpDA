\section{Theoretical Framework}
This section establishes the conceptual foundations necessary to understand scalable smart gardening systems. While building an IoT infrastructure presents significant complexity, standardized reference models provide a framework for structuring such systems. Therefore, this section outlines the required IoT architectures and explores modern cloud backend solutions like Backend-as-a-Service (BaaS). These theoretical building blocks provide the necessary context before evaluating specific architectural implementations.

\subsection{The IoT World Forum Reference Model (7-Layer Model)}
To reason systematically about IoT architectures, this thesis utilizes the IoT World Forum 7-Layer Reference Model as a conceptual map. A layered architecture breaks a complex system into ordered levels, where each layer has a defined role and clear interfaces to the layers above and below it. While alternative models such as the OSI layer model exist, they are primarily oriented towards network communication protocols rather than the holistic integration of hardware, edge computing, and cloud infrastructure required for this use case. The 7-layer model serves as the optimal baseline for understanding the fundamental division between "Fog" (Edge) and Cloud computing.

In the IoT World Forum model, Layer 1 (Physical Devices \& Controllers) represents the ``edge'' hardware such as microcontrollers and their environmental sensors, which directly interact with the physical environment. Layer 2 (Connectivity) covers the communication technologies like Wi-Fi, MQTT, and HTTPS that transport data between devices and backend systems.

Layer 3 (Edge or Fog Computing) contains processing that happens close to the data source, such as filtering, threshold checks, or basic aggregation on a local gateway or directly on the microcontroller. Edge computing is the practice of performing computation near where data is generated, instead of sending everything to a distant cloud, primarily to reduce latency and bandwidth usage. Layer 4 (Data Accumulation) focuses on storing data in transit and buffering it for further processing, for example via message brokers or initial ingestion into a managed database or BaaS platform. Data accumulation in this sense means persisting raw streams in a form that later layers can query reliably.

Layer 5 (Data Abstraction) transforms and structures stored data into more efficient and meaningful representations, such as aggregated views, hypertables in a time-series database, or standardized APIs serving cleaned data. Data abstraction therefore hides storage details and presents a consistent interface to application logic. Layer 6 (Application) contains the business logic and user interfaces, such as a React Native app, notification engine, or gamification components that interpret sensor data and present it to the user. Finally, Layer 7 (Collaboration \& Processes) models how data drives human action and social interaction---for instance, sharing plant status with friends, participating in community leaderboards, or integrating plant health into broader workflows.

In this thesis, a central architectural question is how much decision logic should remain at Layer 3 (Edge) versus being shifted upward into Layer 5 (Data Abstraction) and Layer 6 (Application) in the cloud. The 7-layer model structures this discussion by establishing clear boundaries between physical sensing, connectivity, edge processing, and backend-centric logic.

\subsection{Modern IoT Backends}
The architecture of a modern IoT backend requires a robust foundation that can concurrently handle traditional relational data (like users and profiles) and the unique demands of high-velocity sensor streams. This section explores Backend-as-a-Service (BaaS) and specialized database extensions that address these requirements without the overhead of manually managing complex server infrastructures.

\subsubsection{Backend-as-a-Service (BaaS) and the SQL vs. NoSQL Paradigm}
A Backend-as-a-Service (BaaS) is a cloud computing model that provides developers with outsourced, ready-made backend building blocks such as databases, user authentication, file storage, and serverless APIs. This model abstracts away the underlying infrastructure, allowing development teams to focus predominantly on application logic rather than server provisioning and maintenance. Historically, early BaaS platforms were dominated by NoSQL, document-oriented databases (e.g., Firebase). These systems offer immense flexibility for unstructured data and rapid prototyping, but often pose significant challenges when attempting to execute complex analytical queries or maintain strict relational integrity across diverse data domains \cite{closefuture_supabase_firebase, supabase_alternatives}.

In modern IoT backends, where telemetry streams must often be correlated with structured user profiles and social graphs, a purely document-oriented approach can require complex, manual data denormalization. Consequently, a newer generation of BaaS solutions has emerged that builds the service layer entirely around traditional relational database management systems (RDBMS) like PostgreSQL. These SQL-native platforms attempt to merge the architectural rigor of relational data, including enforcing referential integrity and complex querying, with the managed, real-time event streaming capabilities previously exclusive to NoSQL platforms \cite{blog_elest_supabase_self_host, supabase_alternatives}.

Real-time subscription mechanisms are a critical component of modern BaaS offerings. By exposing database changes over persistent WebSocket connections, the backend can instantly push state changes---such as an updated sensor threshold or a new social message---to connected clients without the overhead of continuous HTTP polling. Platforms such as Supabase represent this modern BaaS approach, utilizing PostgreSQL as the core engine to provide relational integrity alongside native real-time subscriptions.

A central evaluation criterion for selecting a BaaS in an IoT context is its extensibility. While a standard RDBMS excels at transactional consistency (ACID properties), it is fundamentally poorly equipped for high-velocity, continuous sensor ingestion. Theoretical capability hinges on whether the BaaS permits native extensions—such as spatial or time-series modules—to optimize the core relational engine for these specialized workloads without requiring an entirely separate database instance \cite{closefuture_supabase_firebase, blog_elest_supabase_self_host}.

\subsubsection{Time-Series Databases: Why Standard SQL Fails for Sensor Streams}
Relational databases were originally designed for transactional workloads, such as order processing or user management, where each query touches a manageable number of rows and data volumes grow at a moderate pace. For continuous sensor data, this assumption breaks down. High-velocity ingestion describes situations where a system must handle large amounts of incoming data per second---for example, frequent measurements from many sensors---and each new record must be validated, indexed, and written to disk. Under such loads, a traditional relational engine can become the bottleneck.\cite{milvus_rdbms_limitations, tigerdata_tsdb_vs_rdbms}

Most relational systems use a B-tree index, a tree-like data structure that helps the database find rows quickly by sorted keys, but which becomes increasingly expensive to maintain as tables grow very large. In a continuous stream, data never stops arriving; instead of occasional inserts, the system must keep accepting new rows while maintaining indexes and query performance. Over time, query degradation occurs: time-based queries that scan large ranges become slower as the table and its indexes expand, even if only recent data is typically needed. Storage bloat and data retention challenges appear when all historical sensor data is kept indefinitely in the same tables, making backups, index maintenance, and schema changes more and more costly. These scalability problems justify using specialized time-series extensions that optimize for time-based partitioning, compression, and efficient range queries rather than treating sensor data like ordinary transactional records.\cite{tigerdata_tsdb_vs_rdbms, milvus_rdbms_limitations}

\subsubsection{The TimescaleDB Extension: Hypertables and Chunking Explained}
Time-Series Database extensions (such as TimescaleDB for PostgreSQL) turn a standard RDBMS into a time-series--optimized database while keeping the SQL interface and tooling intact. An extension in this sense is an add-on module that plugs into the database and extends it with new capabilities without replacing the core engine. These extensions introduce the concept of a hypertable, which is a logical table that automatically partitions time-series data into smaller physical pieces while still appearing as a single table to the application. This automatic partitioning is implemented through chunking, where each chunk stores data for a specific time interval (and optionally an additional dimension like device ID).\cite{tigerdata_tsdb_compared, tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention}

Chunking exploits temporal locality, the observation that most queries and inserts target recent time intervals and therefore only touch a small subset of all stored data. By mapping new inserts into the latest chunk and allowing queries to skip entire chunks outside the requested time range, these databases enable high-performance inserts and fast time-range queries even when total row counts reach billions. Continuous aggregates are precomputed, automatically refreshed summaries of time-series data (for example, hourly averages or daily minima) that trade some storage and compute for much faster analytical queries over long periods. A retention policy defines rules to automatically drop or compress old chunks after a configured time, so that storage growth remains controlled and the most relevant data stays fast to access.\cite{tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention, tigerdata_tsdb_compared}

Compared to a normal relational table, a hypertable's internal chunk layout reduces the I/O and indexing burden on the database and lets developers keep using standard SQL while benefiting from time-series--specific optimizations.\cite{tigerdata_caggs_retention, tigerdata_tsdb_compared, tigerdata_best_practices_hypertables}

\subsubsection{Object Storage and Media Handling in IoT Scenarios}
In contemporary smart systems, not all generated data consists of structured numerical telemetry. The advent of socially integrated and gamified IoT platforms necessitates the handling of unstructured or semi-structured media, such as user profile pictures, environmental imagery, or video streams. These files are fundamentally incompatible with high-performance relational database storage paradigms. Attempting to integrate binary data directly into a primary SQL database (e.g., storing images as massive BLOBs in tables) inevitably introduces severe performance bottlenecks. The resulting storage bloat dramatically degrades the caching efficiency and read performance critical to the underlying time-series querying mechanisms.

To solve this, system architectures theoretically isolate structured data from unstructured media through the implementation of Object Storage. Object storage is a flat, highly scalable architecture that stores files as 'objects' within buckets, identified by unique keys, and optimized for immense capacity and durability rather than row-based indexing \cite{supabase_s3_docs, deepwiki_supabase_core}. 

This deliberate separation of concerns ensures that the relational database is optimized exclusively for telemetry streams and transactional logic, while the heavy lifting of serving media files is delegated to the specialized object store. Furthermore, object storage systems are frequently coupled with Content Delivery Networks (CDNs), ensuring that large media assets are cached and served from geographically distributed edge locations minimizing latency for the end-user without taxing the core backend servers \cite{supabase_s3_compatible, supabase_storage_github}.

\subsection{Microservices in IoT}

As IoT systems grow, separating the backend into smaller, functional components becomes essential for both stability and development velocity. Microservices represent a distributed architectural style in which system functionality is split into small, independently deployable services, each responsible for a focused capability. This contrasts with monolithic backends where all logic is bundled into a single application and must be deployed as one unit. In the context of scalable architectures, this style allows development teams to separate device communication (MQTT), data storage, and user-facing features into distinct, cooperating components. This separation forces clear interfaces and prevents hardware-specific protocols from tangling with backend business logic \cite{microservices_io_gateway}.

\subsubsection{The Gateway Pattern: Bridging Edge and Core Services}

Architectural patterns are reusable, named solutions to recurring design problems. Within a microservices architecture, the Gateway pattern (often discussed as the API Gateway pattern) describes a service that acts as a single entry point between external clients---in this case, distributed ESP32 microcontrollers---and the internal backend services \cite{microservices_io_gateway, microservices_io_patterns, microservices_io_apigateway}.

For secure IoT deployments, establishing a dedicated Gateway explicitly to bridge the device world (e.g., MQTT) and the data world (e.g., a RESTful BaaS) is a critical structural decision driven by security and scalability requirements. Directly connecting field-deployed microcontrollers to BaaS APIs would necessitate hardcoding database API keys directly onto the microcontroller firmware. This represents a severe security vulnerability, as hardware can be physically compromised or firmware extracted. 

Instead, a middleware gateway acts as a secure buffer. A typical message broker receives published messages from devices and distributes them to subscribed clients based on topics, decoupling the publishers (edge sensors) from consumers (backend databases). The gateway microservice subscribes to these topics and performs protocol translation, converting lightweight MQTT messages into structured database operations \cite{microservices_io_apigateway}. 

Beyond security, this decoupling provides crucial structural flexibility. As the user base scales, the backend infrastructure can be modified without requiring firmware updates across all deployed devices. Furthermore, it enables regional scalability; additional MQTT brokers can be deployed in different geographic regions to minimize device-to-broker latency, while the gateway continues to securely funnel all translated telemetry into the central database instances \cite{digitalapi_gateway_pattern, microservices_io_apigateway}. 

In summary, the Gateway pattern provides a controlled entry point where all device traffic is validated, shaped, and translated before it reaches the core database. This avoids the security risks of hardcoded API keys while ensuring the architecture remains highly modular and geographically scalable \cite{microservices_io_apigateway}.

\subsubsection{Service Inter-communication: Synchronous vs. Asynchronous Patterns}
Inter-service communication describes the fundamental mechanisms by which independent microservices exchange data to fulfill overarching system requests. Synchronous communication requires the calling service to pause its execution (block) while waiting for the receiving service to systematically process the request and generate a direct reply. This is historically implemented via HTTP/REST or gRPC. While synchronicity ensures immediate consistency and guarantees that the caller is aware of the operation's success or failure, it introduces rigid architectural coupling. In a distributed IoT setting, if a downstream database service experiences latency, upstream services—such as the API gateway—are forcefully delayed. Under heavy load conditions, this coupling results in thread exhaustion and cascading system failures \cite{gfg_microservices_communication, gfg_inter_service_communication}.

To mitigate these fatal blocking bottlenecks, highly scalable IoT backends theoretically transition toward asynchronous communication patterns. In an event-driven, asynchronous model, the source service dispatches a lightweight message to an intermediary message broker or queue and immediately resumes its designated tasks, without awaiting a finalized response. 

For architectures processing high-frequency sensor telemetry, this non-blocking paradigm acts as a critical shock absorber. When a fleet of disconnected devices simultaneously regains network access and floods the backend with historical measurements, synchronous APIs theoretically risk server timeouts. Conversely, an asynchronous gateway absorbs the spike by rapidly queueing the incoming payloads. Downstream persistence services then draw from this queue at a sustainable, independent rate. This pattern trades immediate data visibility (eventual consistency) for profound system resilience and high availability \cite{cerbos_inter_service_communication, gfg_inter_service_communication, gfg_microservices_communication, gfg_sync_vs_async_system_design}.

In summary, microservices permit IoT backends to be decoupled into independently deployable units, while the Gateway pattern introduces an essential abstraction layer that structurally isolates internal business logic from raw device communication. Concurrently, the selection between synchronous and asynchronous inter-service workflows actively dictates the system's theoretical resilience to the inherent volatility of vast sensor networks. These abstract architectural decisions form the basis upon which specific technology stacks are evaluated and implemented.\cite{gfg_microservices_communication, microservices_io_gateway, gfg_inter_service_communication, microservices_io_apigateway}

\subsection{Architectural Paradigms: Edge vs. Cloud}

Architectural design in IoT systems is fundamentally defined by the locus of computation. Deciding whether logic resides in the cloud or directly on the microcontroller dictates latency, reliability, and power consumption constraints. 

\subsubsection{Defining the Cloud-Centric Model}

A cloud-centric architecture concentrates the computational load, long-term data storage, and decision-making within remote data centers. The devices at the edge act as "dumb sensors," reading raw environmental values and immediately forwarding them to the cloud for validation, aggregation, and interpretation \cite{digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}.

The primary advantage of this centralization is raw computational power and horizontal scalability. Complex queries, time-series aggregations, and social features can be executed without concern for the strict hardware limitations of an embedded device. However, a purely cloud-centric model is entirely dependent on continuous internet connectivity and is subject to network latency (Round-Trip Time). While minor delays might be acceptable for periodic temperature logging, they can disrupt real-time control loops or immediate user feedback mechanisms \cite{nsf_par_10184999, gfg_cloud_computing, digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}.

\subsubsection{Defining the Edge-Centric Model}

Conversely, an edge-centric architecture pushes computation, data aggregation, and autonomous decision-making down to the local device. The microcontroller is responsible for interpreting its own readings, evaluating thresholds, and triggering local actuation (such as controlling an LED or a water pump) without waiting for cloud instruction \cite{scalecomputing_edge_vs_cloud, scalecomputing_edge_devices, blog_elest_supabase_self_host}.

This model guarantees ultra-low latency and offline fault tolerance. If the external network fails, the device can still protect the plant. Furthermore, bandwidth usage is minimized since only summarized events, rather than raw streams, are transmitted outward. However, moving complex logic to the edge introduces severe development challenges. Firmware updates become complex deployment operations, remote debugging is highly restricted, and the code must operate within the strict CPU, RAM, and battery constraints of microcontrollers \cite{digitalocean_edge_vs_cloud, scalecomputing_edge_vs_cloud, blog_elest_supabase_self_host, scalecomputing_edge_devices}.

\subsubsection{The Spectrum of Logic Distribution: ``Thick Edge'' vs. ``Thin Edge''}

In architectural practice, the allocation of responsibilities between Edge and Cloud does not represent a strict binary, but rather exists dynamically spanning a continuous spectrum. Distinct paradigms evaluate the fundamental trade-off between localized robustness and centralized agility.

A \textbf{``Thick Edge''} architecture delegates substantial processing power, state management, and autonomous control to the deployed microcontroller. This localizes the critical path, guaranteeing offline operational fault tolerance and ultra-low latency response times. If the external network fails, the device retains the capacity to enact crucial logical routines. However, this demands significantly higher-powered hardware nodes and introduces intense deployment complexity. Implementing changes to decision logic mandates costly, distributed over-the-air (OTA) firmware updates, increasing maintenance friction \cite{digitalocean_edge_vs_cloud, scalecomputing_edge_vs_cloud, scalecomputing_edge_devices}.

Conversely, a \textbf{``Thin Edge''} strategy heavily centralizes logic, utilizing edge nodes almost entirely as minimal ingestion vectors. The microcontroller focuses exclusively on immediate sensory acquisition---performing analog-to-digital conversions and structuring transmission payloads---before instantly delegating logical evaluation to remote cloud infrastructure. While this heavily binds the system's functional utility to sustained internet connectivity, it allows for deploying structurally simple, highly cost-effective embedded hardware. More importantly, it centralizes backend business logic, allowing development teams to instantaneously iterate upon complex algorithms, aggregations, and artificial intelligence models without touching the edge hardware framework \cite{blog_elest_supabase_self_host, iotclass_edge_fog_cloud}.

These opposing distributions highlight a profound architectural reality: IoT system design must evaluate whether the specific physical constraints of the target domain necessitate the cost of localized autonomy (Thick Edge) or the developmental scalability of centralized logic (Thin Edge). This theoretical framework serves as the definitive analytical context for evaluating explicit structural decisions and localized logic distributions within concrete IoT ecosystem implementations.
