\section{Theoretical Framework}
This section establishes the conceptual foundations necessary to understand scalable smart gardening systems. It introduces standardized reference models for IoT architectures, explores modern cloud backend solutions like Backend-as-a-Service (BaaS), and details database strategies for handling high-frequency sensor data. These theoretical building blocks provide the context for the concrete PlantUp architecture discussed in Chapter 4.

\subsection{The IoT World Forum Reference Model (7-Layer Model)}
To reason systematically about IoT architectures, this thesis uses the IoT World Forum 7-Layer Reference Model as a conceptual map. A layered architecture breaks a complex system into ordered levels, where each layer has a defined role and clear interfaces to the layers above and below it. In the IoT World Forum model, Layer 1 (Physical Devices \& Controllers) represents the ``edge'' hardware such as ESP32 boards and their moisture, light, and temperature sensors, which directly interact with the physical environment. Layer 2 (Connectivity) covers the communication technologies like Wi-Fi, MQTT, and HTTPS that transport data between devices and backend systems.

Layer 3 (Edge or Fog Computing) contains processing that happens close to the data source, such as filtering, threshold checks, or basic aggregation on a local gateway or directly on the microcontroller. Edge computing is the practice of performing computation near where data is generated, instead of sending everything to a distant cloud, primarily to reduce latency and bandwidth usage. Layer 4 (Data Accumulation) focuses on storing data in transit and buffering it for further processing, for example via message brokers or initial ingestion into a managed database or BaaS platform. Data accumulation in this sense means persisting raw streams in a form that later layers can query reliably.

Layer 5 (Data Abstraction) transforms and structures stored data into more efficient and meaningful representations, such as aggregated views, hypertables in a time-series database, or standardized APIs serving cleaned data. Data abstraction therefore hides storage details and presents a consistent interface to application logic. Layer 6 (Application) contains the business logic and user interfaces, such as a React Native app, notification engine, or gamification components that interpret sensor data and present it to the user. Finally, Layer 7 (Collaboration \& Processes) models how data drives human action and social interaction---for instance, sharing plant status with friends, participating in community leaderboards, or integrating plant health into broader workflows.

\textbf{[Figure 3.1: The 7-Layer IoT World Forum Reference Model]}

In this thesis, the central architectural question is how much decision logic should remain at Layer 3 (Edge) versus being shifted upward into Layer 5 (Data Abstraction) and Layer 6 (Application) in the cloud. The 7-layer model structures this discussion by making it clear which concerns belong to physical sensing, which to connectivity, which to edge processing, and which to backend data management and user-facing features. This layered view also highlights that changes at one level---for example, more intelligence on the edge---directly influence complexity and requirements at the backend layers.

\subsection{Modern IoT Backends}

\subsubsection{Backend-as-a-Service (BaaS): The Role of Supabase in IoT}
A Backend-as-a-Service (BaaS) is a cloud platform that provides ready-made backend building blocks such as databases, authentication, file storage, and APIs, so developers do not need to manage servers, operating systems, and database installations themselves. Supabase is an example of a BaaS that builds its architecture around PostgreSQL as a Postgres-native backend, meaning that all data lives in a relational Postgres database while Supabase generates REST and real-time APIs on top of it. This approach combines the familiarity of SQL with managed infrastructure and additional services like authentication and storage.\cite{closefuture_supabase_firebase, supabase_alternatives, blog_elest_supabase_self_host}

Supabase supports real-time subscriptions by exposing database changes over WebSockets, which are long-lived network connections that allow clients and servers to push messages back and forth without opening a new HTTP request for each update. When a row in a subscribed table is inserted, updated, or deleted, Supabase streams a change event to connected clients, so they can update UI components or trigger backend jobs immediately. The serverless paradigm in this context means that custom logic runs in small, stateless functions that scale automatically with demand, while the developer does not manage or even see the underlying servers. A unified backend describes the idea that authentication, database access, storage, and real-time messaging are provided through one coherent platform with consistent security rules, instead of stitching together several unrelated services.\cite{supabase_alternatives, blog_elest_supabase_self_host, closefuture_supabase_firebase}

\textbf{[Figure 3.2: Supabase Realtime Architecture Flow]}

In a smart gardening setup, such real-time subscriptions allow mobile apps, dashboards, or automation services to react instantly when new sensor measurements arrive or when thresholds are breached. The BaaS model reduces operational overhead for the project and makes it feasible to iterate quickly on backend features while still benefiting from a robust Postgres-based foundation.\cite{blog_elest_supabase_self_host, closefuture_supabase_firebase, supabase_alternatives}

\subsubsection{Time-Series Databases: Why Standard SQL Fails for Sensor Streams}
Relational databases were originally designed for transactional workloads, such as order processing or user management, where each query touches a manageable number of rows and data volumes grow at a moderate pace. For continuous sensor data, this assumption breaks down. High-velocity ingestion describes situations where a system must handle large amounts of incoming data per second---for example, frequent measurements from many sensors---and each new record must be validated, indexed, and written to disk. Under such loads, a traditional relational engine can become the bottleneck.\cite{milvus_rdbms_limitations, tigerdata_tsdb_vs_rdbms}

Most relational systems use a B-tree index, a tree-like data structure that helps the database find rows quickly by sorted keys, but which becomes increasingly expensive to maintain as tables grow very large. In a continuous stream, data never stops arriving; instead of occasional inserts, the system must keep accepting new rows while maintaining indexes and query performance. Over time, query degradation occurs: time-based queries that scan large ranges become slower as the table and its indexes expand, even if only recent data is typically needed. Storage bloat and data retention challenges appear when all historical sensor data is kept indefinitely in the same tables, making backups, index maintenance, and schema changes more and more costly. These scalability problems justify using specialized time-series extensions that optimize for time-based partitioning, compression, and efficient range queries rather than treating sensor data like ordinary transactional records.\cite{tigerdata_tsdb_vs_rdbms, milvus_rdbms_limitations}

\subsubsection{The TimescaleDB Extension: Hypertables and Chunking Explained}
TimescaleDB is a PostgreSQL extension that turns Postgres into a time-series--optimized database while keeping the SQL interface and tooling intact. An extension in this sense is an add-on module that plugs into PostgreSQL and extends it with new capabilities without replacing the core engine. TimescaleDB introduces the concept of a hypertable, which is a logical table that automatically partitions time-series data into smaller physical pieces while still appearing as a single table to the application. This automatic partitioning is implemented through chunking, where each chunk stores data for a specific time interval (and optionally an additional dimension like device ID).\cite{tigerdata_tsdb_compared, tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention}

Chunking exploits temporal locality, the observation that most queries and inserts target recent time intervals and therefore only touch a small subset of all stored data. By mapping new inserts into the latest chunk and allowing queries to skip entire chunks outside the requested time range, TimescaleDB enables high-performance inserts and fast time-range queries even when total row counts reach billions. Continuous aggregates are precomputed, automatically refreshed summaries of time-series data (for example, hourly averages or daily minima) that trade some storage and compute for much faster analytical queries over long periods. A retention policy defines rules to automatically drop or compress old chunks after a configured time, so that storage growth remains controlled and the most relevant data stays fast to access.\cite{tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention, tigerdata_tsdb_compared}

Compared to a normal relational table, a hypertable's internal chunk layout reduces the I/O and indexing burden on the database and lets developers keep using standard SQL while benefiting from time-series--specific optimizations.\cite{tigerdata_caggs_retention, tigerdata_tsdb_compared, tigerdata_best_practices_hypertables}

\subsubsection{Object Storage and Media Handling in Microservices}
Not all data in a smart gardening system is structured sensor data; users may upload images of their plants, profile pictures, or short videos. These files are unstructured or semi-structured and are better handled by object storage rather than by storing them directly in relational tables. Object storage is a service that stores files (objects) in buckets and references them by keys, optimized for durability, scalability, and large binary content instead of row-based queries. Supabase Storage is an example of such a service: it offers S3-compatible, scalable object storage while storing metadata like file paths and permissions in Postgres so that existing access control policies can be reused.\cite{supabase_s3_compatible, supabase_s3_docs, supabase_storage_github, deepwiki_supabase_core}

A Blob (Binary Large Object) is a large binary file---such as an image or video---that is stored as a single object. A Content Delivery Network (CDN) is a distributed network of caching servers that serve static content like images from locations geographically closer to the user, reducing latency and load on the origin storage. Separation of concerns in this context means using the database for structured, relational data (sensor readings, users, devices) and using object storage for binary media, instead of mixing both in one layer. Supabase's storage engine follows this pattern: metadata and authorization are handled in Postgres, while the actual file data is served via multi-protocol object storage endpoints.\cite{supabase_s3_docs, supabase_storage_github, deepwiki_supabase_core, supabase_s3_compatible}

This separation allows microservices to focus on their primary responsibilities. For example, a sensor ingestion service never needs to know where images are stored, and a media service does not need to understand the details of time-series queries. CDN caching strategies further help by offloading frequently accessed media to edge servers, improving performance for users without affecting the core database workload.

\subsection{Microservices in IoT}

Microservices represent a distributed architectural style in which system functionality is split into small, independently deployable services, each responsible for a focused capability. This contrasts with monolithic backends where all logic is bundled into a single application and must be deployed as one unit. In IoT backends, microservices are particularly relevant because they support independent scaling of hot paths (such as sensor ingestion), targeted fault isolation, and parallel development by different teams or individuals. In the context of smart gardening, this style allows us to separate device communication, data storage, notification logic, and user-facing features into clear, cooperating services.\cite{microservices_io_gateway}

\subsubsection{The Gateway Pattern: Bridging Edge and Core Services}

Architectural patterns are reusable, named solutions to recurring design problems, such as how clients reach services or how services communicate. A microservice, in this context, is a small, self-contained backend service that runs in its own process, has a clear responsibility, and communicates with other services over the network. The Gateway pattern (often discussed as the API Gateway pattern) describes a service that acts as a single entry point between external clients or devices and an internal set of backend services, handling routing, security, and protocol translation instead of exposing all services directly. In an IoT scenario, this gateway can be specialized to sit between the device world (MQTT) and the data world (databases and other backend services).\cite{microservices_io_gateway, microservices_io_patterns, microservices_io_apigateway}

Middleware, in this context, means a component that sits between two layers---often the telemetry broker and the database---and transforms, validates, and routes messages between them. A typical message broker is responsible for receiving published messages from devices and distributing them to subscribed clients based on topics, decoupling publishers (sensors) from consumers (backend services). A gateway microservice can subscribe to relevant topics, perform protocol translation by turning telemetry messages into structured database operations (for example, SQL inserts or API calls), and thereby act as a bridge that shields downstream services from device-specific details.\cite{microservices_io_apigateway}

Decoupling means reducing direct dependencies between components so that a change in one part (e.g., device firmware) does not immediately force changes in others (e.g., database schema or application code). Protocol translation is the process of converting one communication format (MQTT messages with topic and payload) into another (database operations or HTTP calls) while preserving the meaning of the data. The gateway can also implement message buffering by temporarily queuing incoming messages when the database is slow or temporarily unreachable, instead of dropping them or blocking the broker. A security boundary arises because the gateway is the only component that talks directly to the outside world, so it can validate authentication tokens, enforce access rules, and prevent devices from accessing internal services directly. Traffic throttling refers to limiting how many requests or writes are forwarded to downstream services per time interval to protect databases and other backends from overload, which is another responsibility that fits naturally into a gateway.\cite{digitalapi_gateway_pattern, microservices_io_apigateway}

In summary, the Gateway pattern provides a controlled entry point where all device traffic is validated, shaped, and translated before it reaches the core backend. This visual separation---message subscription, message handling, normalization, and persistence---highlights the clear responsibilities within the service and shows how the Gateway pattern centralizes external communication while keeping the rest of the backend insulated from device protocols and message noise.\cite{microservices_io_apigateway}

\subsubsection{Service Inter-communication: Synchronous vs. Asynchronous Patterns}
Inter-service communication describes how microservices talk to each other to fulfill a user request or process a device event. Synchronous communication means one service sends a request to another service and waits for a response before continuing, typically using HTTP/REST or gRPC. In this model, the calling service performs a blocking operation: its thread or logical workflow is paused until the callee responds or times out. Immediate consistency is easier to reason about in such setups, because once the response is received, the caller can assume that the callee has already applied its changes and that the shared state is up to date.\cite{gfg_microservices_communication, gfg_inter_service_communication}

Asynchronous communication means a service sends a message and does not wait for an immediate reply; instead, it continues its work while another service processes the message later, often via a message queue or event stream. An event-driven architecture builds on this idea: services emit events (for example, ``sensor value stored'' or ``threshold exceeded''), and other services subscribe to and react to these events without the emitter knowing who listens. Eventual consistency describes the property that different services may temporarily see different states, but if no new updates occur, all replicas converge to the same state after some time. Coupling, in this context, is the degree to which one service depends on the availability, interface, or timing of another; synchronous request-response patterns tend to create tighter runtime coupling than asynchronous, message-based patterns.\cite{cerbos_inter_service_communication, gfg_inter_service_communication, gfg_microservices_communication}

The trade-offs are straightforward but important for IoT backends. Synchronous communication is conceptually simple and fits operations where a service must know the result immediately, such as validating a user token or fetching a configuration before acting, but it can increase coupling and latency because each service call adds another blocking hop in the critical path. If a downstream service is slow or unavailable, the caller is directly affected. Asynchronous communication, on the other hand, improves resilience and scalability because senders can keep working even when receivers are temporarily overloaded, and queues can absorb traffic spikes. The downside is higher complexity---developers must design for eventual consistency, handle out-of-order events, and reason about background processing instead of linear request flows.\cite{gfg_inter_service_communication, gfg_sync_vs_async_system_design, gfg_microservices_communication}

In summary, microservices allow IoT backends to be decomposed into focused, independently deployable services, while the Gateway pattern introduces a controlled entry point that isolates internal logic from direct device communication. At the same time, the choice between synchronous and asynchronous inter-service communication directly shapes latency, reliability, and coupling, which are exactly the dimensions that matter when deciding how much logic to keep at the edge versus offload to the cloud in a smart gardening system. These concepts form the microservice perspective that the next section will apply to the concrete PlantUp architecture.\cite{gfg_microservices_communication, microservices_io_gateway, gfg_inter_service_communication, microservices_io_apigateway}

\subsection{Architectural Paradigms: Edge vs. Cloud}

Architectural design in IoT systems is mainly a decision about where computation and decision-making are performed. Placing logic in the cloud or directly on the device has immediate consequences for latency (how fast the system reacts), reliability (how it behaves during network failures), and power consumption on constrained hardware like the ESP32. In a smart gardening scenario, this essentially means deciding whether the plant sensor only forwards values or also takes responsibility for local decisions.\cite{blog_elest_supabase_self_host, digitalocean_edge_vs_cloud}

\subsubsection{Defining the Cloud-Centric Model}

A cloud-centric architecture is a model in which the computational heavy lifting, long-term data storage, and most decision-making occur in remote data centers operated by cloud providers. The devices at the edge mainly act as ``dumb sensors'': they read raw values and forward them to the cloud, where services such as Supabase or TimescaleDB validate, aggregate, and interpret the data. In this setup, centralized processing means that the core logic is concentrated in a few powerful locations instead of being spread across many small devices.\cite{digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}

The strengths of this approach are straightforward. Cloud platforms offer very high computational power and seamless horizontal scalability, meaning that capacity can be increased by adding more servers of the same type rather than upgrading a single machine. They provide massive storage capacity for time-series and media data, global accessibility via standard internet protocols, and simplified device management because most complexity and updates are handled in the backend instead of on thousands of microcontrollers.\cite{blog_elest_supabase_self_host, digitalocean_edge_vs_cloud}

The weaknesses are closely tied to the same centralization. A cloud-centric architecture depends on continuous internet connectivity; when Wi-Fi or uplink connections fail, devices may lose access to their decision logic. Network latency, often measured as round-trip time (RTT), is the time it takes for a request to travel from the device to the cloud and for a response to come back. Even small RTT values can be noticeable in real-time feedback or control loops. Sending raw sensor data continuously also raises potential privacy concerns and generates ongoing bandwidth costs, especially when many devices are deployed in parallel.\cite{nsf_par_10184999, gfg_cloud_computing, digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}

\subsubsection{Defining the Edge-Centric Model}

An edge-centric architecture pushes computation, data aggregation, and autonomous decision-making down to or near the device that generates the data, such as an ESP32 in the plant pot. Edge-centric architecture means that the microcontroller does not only sample sensors, but also interprets readings, applies thresholds, and can trigger actions locally instead of delegating every decision to the cloud. Local actuation refers to this ability of the device to directly control hardware components like LEDs, pumps, or buzzers based on its own logic.\cite{scalecomputing_edge_vs_cloud, scalecomputing_edge_devices, blog_elest_supabase_self_host}

This model delivers ultra-low latency because decisions are made where the data is produced, without requiring a network round trip. It also provides high fault tolerance: if the internet connection is lost, the core logic can continue running offline and still protect the plant. Bandwidth usage is reduced when only aggregated summaries or events leave the local network, and privacy is improved because detailed raw data can remain on the device or local network segment.\cite{digitalocean_edge_vs_cloud, scalecomputing_edge_vs_cloud, blog_elest_supabase_self_host}

At the same time, edge-centric designs must respect strict hardware constraints: limited CPU performance, RAM, flash storage, and often a tight battery budget on the microcontroller. Firmware updates become more complex, since logic changes must be safely rolled out to many distributed devices that might not always be online. Long-term remote debugging is harder because collecting detailed logs and traces from small devices is limited. Finally, hardware in the field is vulnerable to physical damage or theft, so concentrating all intelligence on the edge can introduce additional risk.\cite{scalecomputing_edge_devices}

\subsubsection{The Spectrum of Logic Distribution: ``Thick Edge'' vs. ``Thin Edge''}

In practice, IoT systems rarely choose only one extreme; instead, they position themselves on a spectrum of logic distribution between device and cloud. Thin Edge describes a cloud-heavy design: the microcontroller reads raw sensor voltage, transmits the unprocessed value to the cloud, and the backend calculates the moisture percentage and decides whether watering is required. Thick Edge pushes more responsibility to the device: the microcontroller reads the sensor, calculates the percentage locally, compares it against an onboard threshold, triggers a local LED alert if needed, and sends only a daily summary or selected events to the cloud.

Logic distribution is the term for how this responsibility for calculations and decisions is split along the edge--cloud axis. Thin Edge favors simpler firmware and powerful central analytics, while Thick Edge favors responsiveness and offline robustness at the cost of more complex device software.

\textbf{The Architectural Trade-off.} This thesis investigates exactly where on this spectrum a consumer IoT device like PlantUp should securely sit in order to balance battery longevity against user engagement, while also considering latency and reliability. Rather than treating Edge and Cloud as mutually exclusive options, the goal is to find a practical hybrid position where local logic is just powerful enough for responsive, fault-tolerant behaviour, and cloud services provide long-term analytics and richer user experiences.\cite{blog_elest_supabase_self_host, iotclass_edge_fog_cloud}
