\section{The PlantUp Architecture}

PlantUp translates the theoretical concepts from Section 3.2 into a concrete architecture for a social smart-gardening system. The design follows the IoT layered model, decomposes backend logic into microservices, and uses a gateway-based approach to abstract device communication. At the same time, it deliberately distributes logic between Edge and Cloud to balance responsiveness, robustness, and long-term analytics.

\subsection{System Overview}

\subsubsection{High-Level Diagram: From Sensor to React Native App}

At the edge, PlantUp uses an ESP32 microcontroller as the primary device in the plant pot. The ESP32 connects to the plant owner's WiFi network and interfaces with attached environmental sensors, such as soil moisture, temperature, humidity, and light sensors. It periodically collects environmental measurements and publishes them into the cloud backend, instead of storing them exclusively on the device. In the IoT World Forum terminology, the sensors and the ESP32 belong to Layer 1 (Physical Devices \& Controllers) and Layer 2 (Connectivity), with basic preprocessing logic on the ESP32 representing Layer 3 (Edge Computing).

The cloud backend is built on Supabase, which provides a Postgres-based database, authentication, and storage as a managed service. Within this backend, PlantUp separates social and application-related data from time-series sensor data through distinct logical schemas: a social schema for users, plants, posts, and interactions, and a micro (or telemetry) schema for controller state and environmental measurements. This reflects Layer 4 (Data Accumulation) and Layer 5 (Data Abstraction) in the IoT model, where data is first ingested and then structured into queryable forms.

On the frontend, a React Native mobile application acts as the main entry point for users. It connects to the cloud backend via secure APIs and real-time subscriptions to display an interactive dashboard with the latest plant state, historical trends, and ``Daily Mentor'' insights generated from the stored data. This corresponds to Layer 6 (Application) and Layer 7 (Collaboration \& Processes), where business logic and social interaction are realized. End-to-end, the data flow runs from sensor measurement on the ESP32, through WiFi into the Supabase backend, and then into the React Native app, which visualizes the information and enables user engagement.

\subsection{The Microservices Layer (Cloud)}

PlantUp's cloud backend follows the microservice principles introduced in Section 3.2.3. Instead of one monolithic application that handles everything from device ingestion to social features, responsibilities are split into logical services. Each service focuses on a specific concern---such as social engagement, device management, or AI insights---and communicates with others over well-defined interfaces. This separation improves maintainability, isolates faults, and makes it easier to evolve individual parts of the system independently.

\subsubsection{Application Layer Services: Gamification, Social, and Engagement}

At the application layer, PlantUp includes several services that focus on user experience and social interaction. A gamification engine tracks experience points (XP), plant growth milestones, and streaks to keep users engaged over time. A social feed service manages posts, comments, and interactions between users, enabling them to share plant statuses and achievements. Media assets such as plant photos are stored using Supabase Storage, which connects object storage with the database's metadata and access control.

Another component is the Daily Mentor, an AI-powered service that generates daily insights or hints based on recent sensor data and user behavior. User authentication and profile management are also implemented as dedicated services that control login, identity, and user-specific preferences. All of these services operate primarily at Layer 6 and Layer 7 of the IoT model and depend on persistent cloud infrastructure. They underline why a pure Edge-only architecture is not sufficient for a Social IoT product---features like social feeds, cross-user comparisons, and AI mentoring inherently require shared cloud resources and data beyond a single device. At the same time, they are logically separated from device state management so that device failures do not directly impact social features.

\subsubsection{Device Management Service (Gateway-Oriented View)}

Alongside the application services, PlantUp includes a dedicated backend service for device management. Conceptually, this service applies the Gateway pattern described in Section 3.2.3: it acts as an abstraction layer between the world of devices and the world of user-facing applications. Instead of letting every service talk directly to devices or raw telemetry tables, the device management service centralizes and normalizes device state.

This service maintains a logical representation of each controller (for example, registration status, last seen timestamp, and basic configuration) and coordinates state changes between the device domain and the application domain. It synchronizes device-originated data into consistent backend structures and exposes a simplified API for other services to query plant status without dealing with low-level details. By isolating device-specific concerns, it provides clear fault isolation: issues with device connectivity or malformed telemetry are handled within this boundary and do not propagate into the social or gamification services. This gateway-oriented view keeps the rest of the backend decoupled from protocol specifics and device lifecycle edge cases.

\subsection{The Data Persistence Layer (Supabase)}

PlantUp uses a unified Postgres-based backend to integrate relational data, time-series telemetry, and media objects within a single managed environment. This aligns with the theoretical view from Section 3.2.2, where a BaaS platform like Supabase provides both relational modeling capabilities and time-series extensions, plus integrated storage for binary data.

\subsubsection{Unified Database Strategy}

At the core, PlantUp relies on a single managed Postgres instance provided by Supabase. Within this instance, the database is structured into logical schemas to keep concerns separated while still allowing cross-schema operations. The social schema contains entities such as users, plants, posts, comments, and gamification-related tables, capturing the ``social graph'' and application state. The micro schema focuses on controller-related entities and sensor measurements, representing the raw and derived environmental data from devices.

Cross-schema querying allows services to, for example, join recent moisture data with plant profiles or user-defined thresholds without duplicating data. The unified access model means that authentication, row-level security, and API generation can be managed consistently across social and telemetry data. Supabase Storage is integrated into this strategy by storing file metadata (e.g., image paths, owners, and permissions) in the same Postgres instance, while actual file blobs reside in scalable object storage. Centralized access control ensures that all data---whether relational, time-series, or media---is protected under the same security and authorization rules. Overall, this reflects the unified backend concept discussed earlier: multiple data types and services share one coherent backend surface.

\subsubsection{Time-Series Integration using TimescaleDB}

To handle sensor telemetry efficiently, PlantUp uses TimescaleDB as an extension inside the same Postgres instance. Environmental measurements (such as moisture, temperature, and light) are stored in hypertables, which partition data by time (and optionally by device) to keep inserts and time-range queries efficient. This design directly addresses the limitations of standard relational tables for high-frequency sensor data discussed in Section 3.2.2.2, where large, ever-growing tables can lead to degraded query performance and heavy index maintenance.

Hypertables and their underlying chunks make it possible to retain long histories of measurements while still answering ``recent trend'' queries quickly, which is essential for historical charts and Daily Mentor insights. The architecture maintains a clear separation between operational workloads---such as user login or social feed interactions in the social schema---and analytical workloads over sensor data in the micro schema. At the same time, it keeps everything in one logical database so that application services can easily combine both views. In this way, PlantUp's persistence layer implements the time-series optimization concepts from Section 3.2.2.3 while staying consistent with the overall unified backend strategy.
