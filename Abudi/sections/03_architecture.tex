\section{The Plant Up! Architecture}

The architectural implementation of Plant Up! builds upon the theoretical concepts established in Chapter 3 to create a functional IoT ecosystem. The design adheres to the IoT World Forum reference model and utilizes a Gateway pattern to manage hardware communication securely. A defining feature of the Plant Up! system is the implementation of a "Thin Edge" paradigm, which centralizes the majority of the processing logic in the cloud. This design choice prioritizes computational scalability and advanced analytical capabilities over localized offline autonomy.

While the architecture is inspired by microservice isolation principles, the backend is deployed as a \textit{modular monolith} using the Supabase Backend-as-a-Service (BaaS) platform. This strategy maintains logical service separation while utilizing a unified database environment for simplified deployment and management.

\subsection{System Overview}

The architecture connects physically deployed edge devices to a scalable cloud backend, which provides processed data to a React Native mobile application. This pipeline ensures consistent remote access and synchronized data across the platform. The physical layer utilizes an ESP32 microcontroller deployed within the plant's environment. The ESP32 interfaces with analog and digital sensors to measure environmental metrics including soil moisture, temperature, humidity, and light intensity. These measurements are periodically structured into standardized JSON payloads for transmission. Within the 7-Layer IoT model, these components represent Layer 1 (Physical Devices) and Layer 3 (Edge Computing). 

The initial pipeline relies on Wi-Fi and MQTT for device-to-cloud communication (Layer 2 - Connectivity). Direct device-to-smartphone technologies, such as Bluetooth Low Energy (BLE), were excluded as they limit real-time remote accessibility and can increase user friction. The Wi-Fi-to-Cloud pipeline supports a seamless onboarding experience and allows users to monitor environmental health globally. A quantitative performance benchmark of the MQTT protocol for this pipeline is presented in Chapter 5.

The core infrastructure uses the Supabase cloud backend, serving as Layer 4 (Data Accumulation) and Layer 5 (Data Abstraction). To accommodate varying data requirements, the database is partitioned into two distinct logical schemas. The \textit{Social} schema manages relational data including user profiles and community features. The \textit{Micro} (telemetry) schema is dedicated specifically to high-velocity time-series sensor data and device states. 

This schema-level separation reduces query complexity for the mobile frontend application (Layers 6 and 7). For example, retrieving user profile data from the Social schema does not require processing telemetry records. This pipeline ensures that sensor measurements generated by the ESP32 traverse the MQTT gateway securely, are partitioned within the PostgreSQL database, and are immediately available for consumption.

\subsubsection{Application Layer Services: Execution and Communication}

The application layer utilizes services integrated within the Supabase ecosystem, which avoids the need for standalone server infrastructure. The mobile application communicates with the backend via REST APIs and WebSocket subscriptions for real-time updates.

Application logic is closely integrated with the persistence layer to optimize execution speed. The gamification engine utilizes native PostgreSQL triggers for low-latency processing. The AI-driven components utilize serverless Supabase Edge Functions. When triggered, an ephemeral container evaluates recent telemetry data from TimescaleDB and interacts with external APIs to generate insights before completing the task. 

Utilizing Edge Functions and database triggers keeps these features decoupled from core IoT data ingestion. If external APIs experience latency, the impact is confined to the specific Edge Function, ensuring that real-time sensor telemetry remains accessible to the user.

\subsubsection{Direct-to-Database Client Architecture and Security}

By utilizing the official Supabase SDK, the mobile application maintains a secure communication channel with the PostgreSQL database, minimizing the requirement for custom intermediary middleware. 

Security is maintained through Supabase Authentication and JSON Web Tokens (JWT). Access control is enforced via Row-Level Security (RLS) policies within PostgreSQL, ensuring that users interact only with authorized social and telemetry data \cite{broadwaySupabase, supabaseReactNative, tigerdataRelational}.

\subsubsection{Device Management Service (Gateway)}

The Device Management Service operates independently of user-facing services and serves as the physical implementation of the Gateway pattern. It acts as the security and protocol boundary between external hardware and the protected backend environment.

This service maintains a boundary between high-velocity telemetry data and relational social data. The mobile application does not execute queries directly against individual sensor tables. Instead, the Device Management Service ingest and normalizes hardware states, including connectivity, registration, and sensor calibration.

By absorbing MQTT payloads, this service translates hardware telemetry into consistent database entries and exposes a simplified, read-only interface for the mobile application. This abstraction protects the frontend from protocol complexities and database management tasks. This isolation ensures that hardware-level issues do not impact the application layer.

\subsection{The Data Persistence Layer (Supabase)}

To manage relational application states, high-velocity telemetry, and user-generated objects, Plant Up! utilizes a consolidated PostgreSQL environment through Supabase. This infrastructure supports both relational modeling and time-series extensions within a unified, managed instance.

\subsubsection{Unified Infrastructure with Schema-Level Isolation}

A unified infrastructural environment simplifies deployment and cross-schema query execution. To maintain data organization, the database is partitioned into distinct logical schemas. The Social schema manages user accounts and interaction metrics, while the Micro (telemetry) schema is dedicated to environmental sensor logs.

This isolation provides organizational clarity and security benefits, supporting Row-Level Security (RLS) policies that manage access to private and public data. Utilizing a single database instance also enables efficient cross-schema queries, allowing the system to join moisture metrics with user-defined thresholds without significant network latency.

\subsubsection{Time-Series Performance Optimization via TimescaleDB}

A requirement of the Plant Up! application is the efficient retrieval of environmental data. While standard relational tables are effective for managing discrete entities, they can experience performance degradation under the high-frequency insertion rates required for sensor telemetry.

To address this, measurements are ingested into TimescaleDB hypertables. TimescaleDB partitions data into temporal chunks, which reduces the indexing burden on the server. By indexing only active temporal chunks (e.g., the last 24 hours of data), the system maintains high retrieval speeds even as database volume increases. This optimization is essential for displaying historical trends and generating AI-driven insights, ensuring a balance between high-velocity ingestion and mobile application performance.
