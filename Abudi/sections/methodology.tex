\section{Methodology}

This section describes the experimental design used to objectively evaluate the architectural decisions made for the PlantUp ecosystem. A core conclusion of Chapter 3 was the theoretical superiority of a Cloud-Centric, ``Thin Edge'' model for this specific botanical domain. To empirically validate this decision, controlled experiments were designed to measure the impact of logic distribution on system latency, scalability, and backend resilience.

\subsection{Experimental Control Framework}

Rather than testing the deployed architecture in isolation, an experimental control group was constructed to facilitate direct comparative analysis. 

\subsubsection{Architecture A: Cloud-Centric (Deployed Variant)}
Architecture A serves as the primary system under test, representing the \textit{Thin Edge} paradigm fully deployed and detailed in Chapter 4. In this variant, the ESP32 hardware functions exclusively as a data ingress vector, generating raw JSON payloads containing sensor telemetry. All threshold evaluation, condition logic, and historical aggregation are executed centrally within the Supabase cloud infrastructure.

\subsubsection{Architecture B: Edge-Centric (Control Variant)}
Architecture B represents a \textit{Thick Edge} mock-up, built strictly as a comparative control group. In this variant, threshold comparison and autonomous decision-making are shifted back directly onto the ESP32 firmware. The device still transmits data to the cloud, but the payloads consist of asynchronous decision logs and state summaries rather than high-frequency raw telemetry. By comparing Architecture B against the deployed Architecture A, the experiment aims to quantify the exact latency penalty and structural trade-offs exacted by the Thin Edge approach.

\subsection{Implementation Constraints}

To ensure that the only independent variable in the experiment is the \textit{location} of the operational logic, both architectures are constrained by identical structural bounds:
\begin{itemize}
    \item \textbf{Hardware:} Both variants execute on the exact same physical ESP32 microcontrollers.
    \item \textbf{Transport:} Both variants utilize identical MQTT message brokers and Wi-Fi environments.
    \item \textbf{Payload Anatomy:} Both variants serialize data into standardized JSON objects, differing only in frequency and semantic content (raw measurements vs. decision logs).
    \item \textbf{Persistence:} Both instances write to identical Supabase endpoints, targeting the same PostgreSQL schemata and TimescaleDB hypertables.
\end{itemize}

\subsubsection{Latency Calculation}
Crucially, end-to-end ingestion latency is not calculated via standard HTTP round-trip bounds, as the MQTT ingress pathway is inherently asynchronous. Instead, latency is empirically derived via differential timestamping. When the ESP32 generates a reading, it injects a highly precise local generation timestamp into the JSON payload. Upon successful ingestion and insertion into the TimescaleDB hypertable, Supabase automatically affixes a \texttt{created\_at} server-side timestamp. The absolute latency per transaction is subsequently calculated by subtracting the ESP32 generation timestamp from the PostgreSQL finalization timestamp, accurately representing the total time required for data transmission, MQTT broker handling, gateway normalization, and final database write.

\subsection{Test Scenarios}

The controlled experiments were structured into two distinct scenarios, designed to evaluate the system under both normal operational cadence and extreme edge-case volatility.

\subsubsection{Scenario 1: Baseline Operational Thresholds}
Scenario 1 serves as the benchmark reference, simulating healthy, standard network conditions. The objective is to record native latency variations and end-to-end response times under standard snapshot intervals (e.g., payloads transmitted every 5 to 10 minutes). The goal is to verify that the fundamental network latency introduced by offloading logic to the cloud (Architecture A) remains comfortably within the loose real-time requirements of botanical monitoring.

\subsubsection{Scenario 2: Infrastructure Stress Test (Disaster Recovery Spike)}
Scenario 2 shifts focus from latency to backend resilience, evaluating how the unified monolithic database degrades under intense transactional stress.

To push the infrastructure to its structural limits, the test suite injects an immediate, simultaneous burst of 1,000 concurrent write operations into the backend API. It is critical to note that this specific volume does not represent a standard ``Daily Active User'' (DAU) load. In normal operation, 1,000 daily users generating 5-minute snapshots produce an exceptionally low continuous ingestion rate of less than one write per second. 

Instead, this concurrency spike mathematically models a massive \textit{Disaster Recovery} event—simulating a widespread ISP or Wi-Fi outage ending, causing an entire fleet of 1,000 disconnected ESP32 devices to regain connectivity and flush their locally queued payloads at the exact same millisecond. By stressing the system with this theoretical worst-case synchronization event, the experiment observes database lock contention, processor queuing, and how rapidly the architecture normalizes once the peak subsides.
