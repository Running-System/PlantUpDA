\section{Theoretical Framework}
Before establishing the technical implementation of a scalable smart gardening system, a conceptual foundation must be established. Designing an IoT infrastructure involves significant complexity, and standardized reference models are essential for organizing this architecture. This section analyzes required IoT models and explores modern cloud solutions, particularly Backend-as-a-Service (BaaS) platforms. These theoretical components are critical for evaluating the design choices implemented in Plant Up!.

\subsection{The IoT World Forum Reference Model (7-Layer Model)}

Analyzing a large-scale, distributed IoT architecture requires a clear structural framework. This thesis utilizes the IoT World Forum 7-Layer Reference Model, which provides a holistic view encompassing physical hardware, connectivity, and cloud services. This model serves as the baseline for differentiating between Edge (or Fog) and Cloud computing \cite{iot_reference_model}.

The model categorizes the ecosystem into seven layers. Layers 1 and 2 (Physical Devices and Connectivity) address edge hardware, sensors, and the network protocols for data transmission. Layer 3 (Edge Computing) involves local processing to minimize latency by handling data close to the source. Layers 4 and 5 (Data Accumulation and Abstraction) manage data buffering and transformation in the cloud, while Layers 6 and 7 (Application and Collaboration) execute business logic and facilitate user interaction.

A central focus of this thesis is the distribution of decision-making logic between local hardware (Layer 3) and centralized cloud services (Layers 5 and 6). The 7-layer model establishes the boundaries necessary for analyzing this computational separation.

\subsection{Modern IoT Backends}
IoT backends must simultaneously handle diverse workloads, including structured relational data (e.g., user accounts) and high-velocity sensor streams. This section explores Backend-as-a-Service (BaaS) platforms and specialized database extensions designed to manage these workloads without requiring manual infrastructure orchestration.

\subsubsection{Backend-as-a-Service (BaaS) and the SQL vs. NoSQL Paradigm}

Backend-as-a-Service (BaaS) provides developers with managed infrastructure, including databases, authentication, and serverless APIs. While early BaaS platforms frequently utilized NoSQL document stores (such as Firebase), these architectures can face challenges with complex analytical queries and relational integrity in advanced IoT ecosystems \cite{closefuture_supabase_firebase, supabase_alternatives}. 

Modern BaaS architectures often utilize Relational Database Management Systems (RDBMS), such as PostgreSQL, which provide data integrity alongside real-time subscription capabilities for mobile clients \cite{blog_elest_supabase_self_host}.

When selecting a BaaS for an IoT ecosystem, extensibility is a critical factor. While standard relational databases ensure transactional consistency (ACID properties), they may require optimization to handle high-velocity sensor streams. Consequently, a BaaS is often enhanced with specialized extensions, such as time-series modules, to optimize the SQL engine for sensor data ingestion \cite{closefuture_supabase_firebase, blog_elest_supabase_self_host}.

\subsubsection{Time-Series Databases: Challenges with Standard SQL for Sensor Streams}

Traditional relational databases, while effective for standard transactional workloads, can experience performance issues when managing high-velocity IoT sensor streams \cite{tigerdata_tsdb_vs_rdbms}. A primary cause is index degradation. 

Standard B-tree indexes can become resource-intensive to maintain as table sizes increase with continuous telemetry data. High ingestion rates can lead to significant RAM consumption by the index, potentially impacting read query performance and server stability. To address this, specialized time-series extensions are implemented to replace standard indexing with time-based partitioning \cite{milvus_rdbms_limitations}.

\subsubsection{The TimescaleDB Extension: Hypertables and Chunking}
TimescaleDB is an extension for PostgreSQL designed to optimize the handling of time-series data while maintaining a standard SQL interface. This allows developers to utilize native SQL queries while benefiting from time-series optimizations.

TimescaleDB manages data through \textit{hypertables}, which appear as standard tables to the application but are partitioned into smaller physical "chunks" based on time intervals (e.g., daily or weekly) \cite{tigerdata_tsdb_compared, tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention}.

This partitioning exploits temporal locality, as most queries and inserts in sensor monitoring target recent data. By directing new inserts to the active chunk, the system avoids scanning historical data, enabling efficient ingestion and rapid range queries even for large datasets.

Additionally, these extensions support continuous aggregates, which precompute data summaries (e.g., daily temperature averages) in the background. Data retention policies can also be configured to compress or remove historical data, managing storage requirements while ensuring that recent data remains accessible \cite{tigerdata_best_practices_hypertables, tigerdata_timescale_alternatives, tigerdata_caggs_retention, tigerdata_tsdb_compared}.

In summary, a hypertable's chunked layout reduces the I/O and indexing burden on the server compared to standard relational tables, providing both standard SQL compatibility and time-series performance \cite{tigerdata_caggs_retention, tigerdata_tsdb_compared, tigerdata_best_practices_hypertables}.


\subsection{Microservices in IoT}

As IoT systems expand, monolithic architectures, where all features are integrated into a single unit, can present challenges for stability and maintenance. 

To ensure stability and development efficiency, modern scalable architectures often utilize microservices. This approach partitions system functionality into focused, independent services. Adopting microservices allows for the separation of external device communication, including MQTT brokers, from user-facing features, facilitating clearly defined interfaces and modularity \cite{microservices_io_gateway}.

\subsubsection{The Gateway Pattern: Bridging Edge and Core Services}

The Gateway pattern (often implemented as an API Gateway) serves as a security and protocol boundary between external clients and protected backend services. It provides a controlled entry point between edge hardware, such as ESP32 microcontrollers, and the internal database \cite{microservices_io_gateway, microservices_io_patterns, microservices_io_apigateway}.

A dedicated Gateway is essential for IoT security. Direct database access from edge devices would require embedding API keys in firmware, which presents a significant security risk if the hardware is compromised. 

Instead, a Gateway serves as a buffer. Edge sensors publish telemetry to a message broker, and the Gateway service, positioned within a secure cloud network, subscribes to these messages, translates the payloads, and formats them for database operations \cite{microservices_io_apigateway}. 

This decoupling also provides structural flexibility, allowing for backend updates without requiring firmware changes on deployed devices. Furthermore, it supports geographical scalability by allowing multiple MQTT brokers and local Gateways to funnel data to a central instance \cite{digitalapi_gateway_pattern, microservices_io_apigateway}. 

Ultimately, the Gateway pattern ensures that device traffic is validated and structured before interacting with the database, enhancing overall security and modularity \cite{microservices_io_apigateway}.

\subsubsection{Service Inter-communication: Synchronous vs. Asynchronous Patterns}

Microservices rely on specific data exchange mechanisms that influence system reliability. Synchronous communication (e.g., HTTP REST) requires the requesting service to wait for a response, which can lead to cascading delays in high-traffic sensor networks \cite{gfg_microservices_communication}.

To manage traffic volatility, scalable architectures frequently utilize asynchronous communication. In an event-driven model, a service publishes a message to a broker and continues its tasks without waiting for a reply \cite{gfg_sync_vs_async_system_design}. This approach facilitates system resilience; for example, if many devices reconnect simultaneously, an asynchronous Gateway can queue the traffic, allowing the database to process data at a sustainable rate \cite{cerbos_inter_service_communication}.

\subsection{Edge vs. Cloud}

IoT architectural design is fundamentally influenced by the location of computational execution. The decision to place logic in the cloud or on the edge microcontroller impacts latency, reliability, and power consumption.

\subsubsection{Defining the Cloud-Centric Model}

A cloud-centric architecture centralizes processing, storage, and decision-making algorithms within remote data centers. Physical devices at the edge serve as "thin" components, recording environmental data and transmitting it to the cloud for interpretation and action \cite{digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}.

The primary advantage of this model is the availability of centralized computational power, allowing for complex time-series aggregations and the integration of advanced features without being limited by edge hardware constraints. However, cloud-centric models are dependent on reliable network connectivity and are subject to network latency. While a delay of several seconds may be acceptable for periodic data logging, real-time control loops may require lower response times \cite{nsf_par_10184999, gfg_cloud_computing, digitalocean_edge_vs_cloud, blog_elest_supabase_self_host}.

\subsubsection{Defining the Edge-Centric Model}

An edge-centric architecture emphasizes localized computation and autonomous decision-making on the edge device itself. The microcontroller interprets local readings and triggers actions (e.g., sensor alerts or pump activation) without requiring a server response \cite{scalecomputing_edge_vs_cloud, scalecomputing_edge_devices, blog_elest_supabase_self_host}.

By performing logic locally, this model provides offline fault tolerance and low latency. It also minimizes bandwidth consumption by transmitting only summarized data to the cloud. However, implementing complex logic on edge devices can increase development and maintenance complexity. Firmware updates and remote debugging can be more challenging compared to centralized cloud deployments. Additionally, developers must work within the CPU and RAM constraints of embedded hardware \cite{digitalocean_edge_vs_cloud, scalecomputing_edge_vs_cloud, blog_elest_supabase_self_host, scalecomputing_edge_devices}.

\subsubsection{The Spectrum of Logic Distribution: ``Thick Edge'' vs. ``Thin Edge''}

In systems engineering, the choice is often not a binary one between Edge and Cloud, but rather a point on a spectrum of logical allocation. 

A \textbf{``Thick Edge''} architecture delegates significant processing and control to the edge device, enhancing localized resilience and minimizing latency. However, this often requires more capable hardware and can increase the complexity of over-the-air (OTA) updates and long-term maintenance \cite{digitalocean_edge_vs_cloud, scalecomputing_edge_vs_cloud, scalecomputing_edge_devices}.

In contrast, a \textbf{``Thin Edge''} strategy centralizes logic in the cloud. Edge hardware is utilized primarily for data acquisition and transmission, with minimal localized processing. This approach relies on continuous connectivity but allows for simpler edge hardware and easier central updates to application logic. It enables development teams to iterate on algorithms and features without requiring direct hardware modifications \cite{blog_elest_supabase_self_host, iotclass_edge_fog_cloud}.

The choice between these models depends on the specific requirements of the application, balancing factors such as localized autonomy (Thick Edge) and developmental scalability (Thin Edge).
